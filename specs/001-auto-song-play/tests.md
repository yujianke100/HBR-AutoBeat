# Test Cases: 自动打歌 - 选难度、自动切歌与自动打歌

本文件将 `spec.md` 中的 Success Criteria 转换为可执行的验收/回归测试用例。注意：由于需要在真实游戏环境中运行，很多测试需要人工或半自动化执行；文档中同时给出可自动化的日志/度量建议以便记录指标。

## 测试环境准备
- 在目标 Windows 机器上安装并激活项目的虚拟环境（同 `requirements-dev.txt`），并确保 `main.py` 能在该环境下运行。
- 提前准备 1-3 首已知谱面的测试歌曲，记录每首歌在手动正常操作下的基线命中数据（用于对比）。
- 日志级别设为 INFO/DEBUG，确保会话日志包含时间戳（ms 精度）、事件标签（start_song, end_song, press, miss, error）、按键 id 与屏幕判定时间。

## 自动化/半自动化测试用例

TC-001: 启动并进入自动打歌（对应 SC-001）
- 前置条件：游戏窗口已识别，按键映射已加载。
- 步骤：在工具中选择目标难度，点击“开始自动”。
- 期望：系统在 <=5s（从点击开始计时）内进入自动打歌状态并产生日志事件 `auto_start`；随后开始发送按键事件且有首个 `press` 事件记录。
- 验证方法：检查会话日志时间戳，确认 `auto_start` 与第一个 `press` 间隔 <=5s。

TC-002: 自动切歌延迟（对应 SC-002）
- 前置条件：队列中至少 2 首歌，开启自动切歌。
- 步骤：播放队列的第一首并等待其结束。
- 期望：从 `end_song` 事件到下一首 `auto_start`（或第一个 `press`）不超过 3s。
- 验证方法：分析会话日志，计算两事件时间差，记录为切歌延迟。

TC-003: 命中率校准与参考（对应 SC-003）
- 前置条件：选择代表性曲目并设置默认 `Press Time`。
- 步骤：运行自动打歌完整谱面一遍，记录命中 / 早按 / 晚按 / 未击中的统计。
- 期望：记录到的命中率作为参考（SC-003 中的 85% 为参考值）；测试记录应包括按键时间偏移分布。
- 验证方法：根据日志计算命中率（hits / total_notes），并导出 CSV 以供离线分析。

TC-004: 稳定性测试（对应 SC-004）
- 前置条件：配置自动队列或循环播放一首歌。
- 步骤：持续运行 30 分钟以上，监控进程是否崩溃、异常日志或资源使用急剧上升。
- 期望：进程不崩溃，若出现错误则安全停止并产生日志条目 `error` 带错误原因。
- 验证方法：检查运行期间的日志与操作系统事件（如进程退出码），并收集内存/CPU 峰值快照。

TC-005: 错误处理（对应 FR-007）
- 前置条件：模拟不可恢复错误（例如：临时关闭游戏窗口或断开输入注入权限）。
- 步骤：在运行中触发该错误。
- 期望：系统记录 `error`，停止自动并向用户展示可理解的错误消息。
- 验证方法：观察 UI 提示与日志记录。

## 自动化建议与脚本
- 日志格式建议：JSON 每行一条，包含 fields: ts_iso, ts_ms, event, song_id, note_index, key_id, avg_offset_ms, detail。
- 可扩展的自动化脚本：编写一个简单的 `tools/measure_latency.py` 来从会话日志中抽取 `end_song` 与 `auto_start` 间隔、命中率与偏移直方图（示例脚本可由我生成）。

## 人工测试说明
- 由于游戏内状态和反作弊等不可控因素，最终判定是否成功需由你在目标机器/真实游戏场景中验证。请在每次测试后将会话日志提交到 `tests/artifacts/` 以便回溯分析。

## 可验收门槛（建议）
- 单次演示：功能在一首代表性曲目上成功运行一遍且能记录日志。
- 回归门槛：所有自动化/手动测试（TC-001..TC-005）通过；切歌延迟均 <=3s；无崩溃记录；日志完整可导出。
